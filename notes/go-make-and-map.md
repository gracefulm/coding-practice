# Go の make と map の容量指定

`make` で渡せる引数と、map を作るときに容量を指定する意味をまとめる。

## make の引数

渡せる引数の数と意味は型によって違う。

| 型 | 書き方 | 2番目の引数 | 3番目の引数 |
|---|---|---|---|
| スライス | `make([]int, len, cap)` | 長さ（この数だけゼロ値が入る） | 容量 |
| map | `make(map[int]int, hint)` | 容量のヒント | なし |
| チャネル | `make(chan int, size)` | バッファのサイズ | なし |

- スライスに長さと容量の2つがあるのは、`make([]int, n)` とすると最初から n 個のゼロ値が入り、`s[i]` でアクセスできるから
  - 「中身がいくつ入っているか」と「どこまで再確保なしで伸ばせるか」を別々に指定する
- map は `make` した直後は必ず空（`len(m) == 0`）。キーを決めずにゼロ値の要素を入れておくことはできないので、長さを指定する意味がない
- そのため `make(map[int]int, 0, n)` はコンパイルエラーになる

```txt
invalid operation: make(map[int]int, 0, n) expects 1 or 2 arguments; found 3
```

**ポイント: スライスの `make([]int, 0, n)` にあたる map の書き方は `make(map[int]int, n)`。**

## map の容量指定で何が起きるか

### スライスの場合（比較用）

`append` で cap を超えると、大きい配列を新しく確保し、中身を**そのままコピー**する。要素の位置は変わらない。

### map の場合

- map の中身はハッシュテーブル（要素を入れる枠 = スロットの配列）
- キーをどのスロットに置くかは、**キーのハッシュ値とテーブルの大きさ**で決まる
- テーブルが混むと探す手間が増えるので、一定の割合が埋まるとテーブルを大きくする
  - Go 1.24 以降の実装（Swiss Table）では、埋まった割合が 7/8 を超えたとき
- テーブルの大きさが変わると、各キーを置くべき位置も変わる
  - そのため単純なコピーでは済まず、**全要素のハッシュ値から位置を計算し直して入れ直す**（再ハッシュ）
- 容量を指定すると、その数を入れるまで拡張が起きないだけのスロットを最初に確保する

### スライスとの違い

| | スライス `make([]T, 0, n)` | map `make(map[K]V, n)` |
|---|---|---|
| 指定した値の意味 | cap（正確な容量） | ヒント（目安） |
| 中身の確認方法 | `cap(s)` で見られる | 見る方法はない（`cap(m)` はコンパイルエラー） |
| 超えたとき | 新しい配列を確保してコピー | 新しいテーブルを確保して全要素を再ハッシュ |
| 指定しなかった場合 | 小さく始めて倍々に拡張 | 同じく小さく始めて段階的に拡張 |

- どちらも指定した数を超えて入れること自体はできる（拡張が起きるだけ）
- 入れる要素数の上限が分かっているなら指定しておく

## map の読み書きの実測値

環境: Apple M2 / Go 1.26.2 / `go test -bench -benchmem`
条件: 要素数 10^4、キーは ±10^9 の範囲のランダムな int

| 操作 | 1回あたり | メモリ確保（10^4 個入れる全体） |
|---|---|---|
| 読み込み（キーがある） | 約 8 ns | なし |
| 読み込み（キーがない） | 約 10 ns | なし |
| 書き込み（容量指定あり） | 約 11 ns | 33 回 / 約 290 KB |
| 書き込み（容量指定なし） | 約 33〜46 ns | 79 回 / 約 580 KB |
| 比較用: スライスを順に読む | 約 0.8 ns | なし |

- map の操作はスライスの連続アクセスより**1桁遅い**。ハッシュ計算とスロットを探す処理が入るため
- 容量を指定すると、書き込みが**約3倍速く**なり、メモリ確保の回数と量もおよそ半分になる
- キーがない場合の読み込みは、ある場合より少し遅い
- この規模（約 300 KB）は CPU キャッシュに収まる。数百万要素のように大きくなるとキャッシュミスが増え、1回あたり数十〜100 ns 以上に伸びることがある

### 例: 1. Two Sum（hashmap 解法）

最悪ケースで読み込み・書き込みがそれぞれ約 10^4 回。

- 容量指定あり: 10^4 × (10 + 11) ns ≈ **0.2 ms**
- 容量指定なし: 10^4 × (10 + 35) ns ≈ **0.45 ms**

二重ループ（比較 約 5 × 10^7 回 ≈ 数十 ms）より 100倍前後速い。
