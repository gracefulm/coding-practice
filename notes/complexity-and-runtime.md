# 計算量と実行時間の見積もり

コードを書く前に「制約の最大値で、このアルゴリズムは時間内・メモリ内に収まるか」を確認する。

- 参考
  - <https://github.com/n6o/leetcode_arai60/pull/10/changes#r2781856580>

## 見積もりの手順

1. 問題の制約から、入力サイズの最大値を確認する（例: `n <= 10^5`）
2. アルゴリズムの計算量の式に最大値を代入し、おおよその操作回数を出す
3. 操作回数を「1秒あたりに処理できる回数」で割って、実行時間を見積もる
4. 同じように、データ構造に入る要素数からメモリ使用量も見積もる

### 例: 373. Find K Pairs with Smallest Sums（step1 の失敗）

制約は `nums1.length, nums2.length <= 10^5`。全ペアをヒープに入れる方法だと次のようになる。

- 時間: n·m 回の `heap.Push` で O(n·m·log(n·m))
  - 10^10 × log₂(10^10) ≈ 10^10 × 33 ≈ 3.3 × 10^11 回の操作
  - 下の実測値では Push 1回が数十 ns なので、10^10 回 × 数十 ns ≈ **数百秒** → TLE
- メモリ: ペア（int 2つ = 16バイト）× 10^10 個 ≈ **160GB** → OOM（実際に `fatal error: runtime: out of memory` になった）

入力がソート済みであることを使い、ヒープに入れるのを `min(k, n)` 個に抑えると、O(k·log min(k, n)) ≈ 10^4 × 14 ≈ 1.4 × 10^5 回で済む。

### O(n·m·log(n·m)) の log はどこから来るか

`log(n·m)` は **`heap.Push` を1回呼んだときのコスト**にあたる。

```go
for _, num1 := range nums1 {          // n 回
	for _, num2 := range nums2 {      // m 回
		heap.Push(&mh, towNums{...})  // ← 1回あたり O(log(ヒープのサイズ))
	}
}
```

#### Push 1回が O(log s) になる理由

`heap.Push` の中では次の2つが行われる。

1. 自分で実装した `Push` で、新しい要素をスライスの**末尾**に追加する
2. `container/heap` 内部の `up` で、その要素を**親と比べ、親より小さければ入れ替える**。これを親の方が小さくなるか、根に着くまで繰り返す

ヒープは完全二分木なので、各段の要素数は 1, 2, 4, 8, … と倍々に増える。要素数を s とすると、**木の高さは約 log₂ s** になる。

```txt
            1            ← 1段目 (1個)
         /     \
        3       2        ← 2段目 (2個)
       / \     / \
      7   4   5   6      ← 3段目 (4個)
     /
    0  ← 新しく末尾に追加 → 7, 3, 1 と入れ替わって根まで上がる
```

最悪の場合は葉から根まで上がるので、比較と入れ替えが高さの分、つまり **log₂ s 回**かかる。
Pop も同じで、末尾の要素を根に移してから下へ入れ替えていく（`down`）ので O(log s) かかる。

#### s が n·m になる理由

step1 では Pop せずに全ペアを Push し続けるので、ヒープのサイズは 1, 2, 3, … と増え、最後は **n·m** になる。

- Push 1回のコストは最大 O(log(n·m))
- Push の回数は n·m 回
- 合計 **O(n·m · log(n·m))**

序盤はヒープが小さいので、1回のコストも小さい。それでも n·m 回分を足し合わせると
log(1) + log(2) + … + log(n·m) = log((n·m)!) となり、これはおおよそ n·m·log(n·m) と同じ大きさになる。そのためオーダーは変わらない。

#### 改善版との違い

改善版ではヒープのサイズが常に **min(k, n) 以下**に抑えられる。
そのため Push / Pop 1回のコストは O(log min(k, n)) になる。これが O(k·log min(k, n)) に出てくる log の部分。

**ポイント: ヒープを使う解法では「何回操作するか」と「ヒープが最大でいくつになるか」を分けて考える。**

## 1秒あたりの処理回数の目安

- **安全な目安: 10^8 回の操作なら 1秒以内に収まる**（LeetCode などで広く使われる目安）
- 操作の種類によって 1回のコストは数十倍違う（下の実測値を参照）
  - 単純な算術・スライスの連続アクセス: とても速い
  - map の操作、ヒープの操作、メモリ確保（`append` によるスライス拡張、`new`）: 遅い
- 見積もりは桁が合えば十分。「10^7 なら余裕、10^9 なら危ない、10^10 以上はまず無理」程度で判断する

### CPU の周波数との関係

- 3GHz は 1秒に 3 × 10^9 クロックという意味
- 1回の操作にかかるクロック数は、操作の内容やキャッシュヒット・ミス、分岐予測などで大きく変わる
  - 単純な加算なら 1クロックに複数回実行されることもある
  - キャッシュミスでメインメモリまで取りに行くと 100クロック以上かかる
- そのため、周波数から実行時間を正確には計算できない。上限の目安（1秒に数×10^9 回より速くはならない）として考える

## Go の実測値

環境: Apple M2 / 16GB / Go 1.26.2 / `go test -bench`

| 操作 | 1回あたり | 1秒あたりの回数 |
|---|---|---|
| 単純な加算ループ（`s += i`） | 約 0.3 ns | 約 3 × 10^9 |
| スライスの連続アクセス（`s += a[i]`） | 約 0.5 ns | 約 2 × 10^9 |
| map への書き込み（キー 6.5万種類） | 約 7 ns | 約 1.4 × 10^8 |
| `container/heap` の Push + Pop（サイズ 10^4） | 約 73 ns | 約 1.4 × 10^7 |

- ヒープの操作は単純なループより **200倍以上遅い**。`any` を経由するインタフェース呼び出しと、log n 回の比較・入れ替えがかかるため
- 単純な加算はコンパイラの最適化が効きやすいので、実際のコードではもっと遅くなると考える

## 制約から使える計算量を逆算する

1秒あたり 10^8 回を目安にした場合の、使える計算量の上限。

| n の最大値 | 使える計算量の目安 | 代表的なアルゴリズム |
|---|---|---|
| 10 程度 | O(n!) | 順列の全探索 |
| 20 程度 | O(2^n) | 部分集合の全探索、bit DP |
| 500 程度 | O(n³) | 3重ループ、区間 DP |
| 10^3〜10^4 | O(n²) | 2重ループ |
| 10^5〜10^6 | O(n log n) | ソート、ヒープ、二分探索 |
| 10^7 以上 | O(n) / O(log n) | 1回の走査、二分探索 |

制約が `n <= 10^5` なら「O(n²) は無理なので O(n log n) 以下の方法を探す」というように、解法を考える手がかりにもなる。

## メモリの目安

| 型 | サイズ |
|---|---|
| `int`, `int64`, `float64`, ポインタ（64bit 環境） | 8バイト |
| `int32` | 4バイト |
| `bool`, `byte` | 1バイト |
| スライスのヘッダ（ポインタ + len + cap） | 24バイト |
| `string` のヘッダ（ポインタ + len） | 16バイト |

- `[]int` の要素 10^6 個 ≈ 8MB、10^8 個 ≈ 800MB
- `[][]int` は内側のスライスごとにヘッダ 24バイトと別のメモリ確保が加わるので、見た目より多く使う
- map は要素数に対して、キーと値の合計サイズの数倍のメモリを使う
- LeetCode のメモリ制限は数百MB 程度なので、要素数が 10^8 を超えそうなら方針を見直す
