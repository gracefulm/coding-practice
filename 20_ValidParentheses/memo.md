# 20. Valid Parentheses

<https://leetcode.com/problems/valid-parentheses/>

## Step1

- 20分くらいで3回くらい提出してPass
- 考えたこと
  - 括弧がネストする場合は、一番先頭の括弧が一番最後に出現する
    - →先入後出し
  - 素のスライスをそのまま使うことも考えたが、ぱっと見でスタックとして使っていることがわかるように構造体を実装
  - 文字列をforで回しながら
    - 始め括弧を見つける
      - 始め括弧を見つけたらスタックにペアとなる終わり括弧をスタックにPush
    - 始め括弧以外の文字列=終わり括弧なのでスタックからPopして比較
      - 文字列が不一致の場合はfalse
    - `[(hoge)]`のような文字列を構成する要素が括弧以外も入るという要件が加わった場合はカバーできないが、一旦考えないで実装

## Step2

- 他の人のPRの確認とAIレビューにより、Step1をブラッシュアップする
  - <https://github.com/miyataka/coding-practice/pull/6>
    - 括弧のペアを保持するmapの型をruneにしており、確かに`map[string]string`にする必要はないと理解した
      - `map[rune]rune`を選択する場合と`map[string]string`を使う場合をAIにベンチーマークを取らせてみると`map[string]string`は以下のコストがかかることが確認できた
      - 変換コスト — string(r) は1文字ごとにランタイム呼び出しで新しい文字列を組み立てる
      - 比較コスト — *expected != char の文字列比較は runtime.memequal を呼び出す（長さ比較＋バイト列比較）一方、rune/byte ならCPU命令1つの整数比較でOK
      - マップキーのハッシュコスト — map[string]string は mapaccess2_faststr（ポインタ経由で文字列の中身をハッシュ）、map[rune]rune は mapaccess2_fast32（32bit整数の単純ハッシュ）
    - mapの変数名について
      - openToCloseという命名が使われている
      - 確かに直感的で情報量が多いので良いと思った
      - step1では、bracketPairsとしており、このままでも十分理解できるとも思う
  - <https://github.com/minsrd/arai60/pull/6>
    - stackに番兵を置けば`len(stack)>0`の確認が不要になる
      - なるほどぉ
      - 選択肢として知っておく
  - その他AIレビュー
    - stack#pop()の戻り値をポインタにしないでcomma-okを使う
      - ポインタを返すより壊れにくい(安全)
      - popのコード量が多くなった時に、コンパイラのインライン化の対象にならずにヒープアロケーションが発生する可能性がある
    - push(char string) / 呼び出し側の val は、実際にpushしているのが「対応する閉じ括弧」なので expectedClose 等のほうが意図が明確
  - その他
    - Goのシングルクオートとダブルクオート
      - 'a' -> rune literal
      - "a" -> string literal
      - `a` -> raw string literal
    - stack生成時にスライスのサイズを指定できるとサイズがでかい入力があった際にアロケーションの回数を抑えることができる
      - ただしデメリットもある
        - 早い段階でfalseと判定されるもの
        - `[]{}[][]()...`のようなスタックの要素数が増えないもの
    - 今回のケースだとswitch-caseを使った方が早い
      - ただ、これ以上括弧の種類とかが増えた時にコードが煩雑になりそう
